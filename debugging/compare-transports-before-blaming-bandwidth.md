# 分不清 TCP 和 UDP，就别急着怪带宽

**远程桌面、串流一类工具卡顿时，先用同一条路径做一次 TCP 对照，再谈带宽。**

## 为什么

一次真实的排查：同一个目标机器、同一条线路，A 工具（走 TCP）流畅，B 工具（走 UDP）持续 30% 以上丢包、帧率掉到 1。

期间逐个排除过：Wi-Fi、本机网卡、代理的 TUN 模式、服务端本身、远端上下行带宽——**全部正常**。带宽测出来下行 640 Mbps、上行 64 Mbps，可 B 工具就是不动。

问题最后落在 UDP 通路上：这条线路对持续 UDP 流的 QoS 处理很差，TCP 正常、UDP 被降级。

## 怎么用

**对照实验**：同一台目标机，同一时间，跑一个走 TCP 的工具和一个走 UDP 的工具。如果前者正常、后者丢包，别再查带宽了。

**看丢包，不看速度。** 带宽测试跑的是 TCP，它正常不代表 UDP 正常。反过来也一样。

**换网络做二次确认。** 用手机热点跑一次，丢包归零就说明是原线路的问题，跟软件无关。

**处置方向**：

- 换成走 TCP/443 的方案，或者让 VPN 走中继（DERP 之类）而不是直连
- 降码率、降分辨率，减少对 UDP 通路的依赖
- 找线路提供方确认是否有 UDP 限速

## 一条推论

**「带宽够但就是卡」不是矛盾，是两个不同的问题。** 吞吐和延迟/丢包是分开的指标，测了前者不代表答了后者。
