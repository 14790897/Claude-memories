# OOM 看起来像「什么都没发生」

**调度器里被 cgroup 杀掉的任务，通常只留下一行日志，不会告警。**

## 为什么

容器设了 `mem_limit`，超了内核就杀进程，退出码 `rc=137`。而调度器对这件事的处理是——打印一行「结束 rc=137」，然后继续。

面板上的数字不会崩，只是**永远不更新**。看起来像「这个任务今天没跑」，其实是「跑了，每次都被杀」。

## 怎么排查

```bash
docker logs <container> | grep 'rc=[1-9]'
```

`rc=137` 就是 OOM。连续多次同一个任务出现 137，基本可以定性。

## 「单独跑能过」不等于「在调度器里能过」

这条最容易骗人。`docker run -m 768m` 手动跑一遍，44.9 秒跑完 `rc=0`，看着没问题——但定时任务仍然 137。

原因有三层：

1. cgroup 上限是**整个容器**的，不是单个进程
2. 同一分钟还有别的任务在跑，内存叠加
3. 数据规模一直在长，昨天够用今天就不够

**验证必须在调度容器内部用 `docker exec` 跑**，不能在旁边单独起一个容器。

## 修法

改 `mem_limit` 之后**必须 `up -d <service>` 重建容器**——`restart` 不会重新读配置。`docker update --memory` 可以立即生效不重启，但不会写回 compose，下次重建会回退。

## 推广

**任何「进程被外部杀掉」的情况，退出码都是唯一线索。** 只要调度器/守护进程只记录退出码不报警，就要自己去 grep 它。
