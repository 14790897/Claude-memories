# heredoc 打补丁会吃掉反斜杠

**改代码用编辑工具，不要用 `python - <<'EOF' ... str.replace(...)` 这类 heredoc 脚本去改含转义的内容。**

## 为什么

想在一个正则里写 `\b`（词边界），经过 heredoc 那一层转义后写进文件的是**真正的退格字符 0x08**。

后果不是报错，是**静默改坏语义**：

- `lists\b` 变成 `lists<BS>`，那条规则**永远匹配不到任何输入**
- 后来给另一个正则加 `\b` 时又犯了同样的手误
- 0x08 在终端里渲染不出来（退格会把前一个字符擦掉），`cat` / `sed` 看那段代码完全正常

**只有按字节读才能发现**：`open(p,'rb').read().count(b'\x08')`。

同一文件里同时存在两处，是因为两条测试挂了才去查字节的。

## 怎么用

- 改多行代码用 Edit 工具，它不引入转义层
- 必须批量替换时，**替换文本里不要出现反斜杠**；非要有，用 `chr(92)` 拼
- 补丁写完必须**验证真的改对了**，别只看 `grep` 出来的那一行——渲染会骗人

## 另外两种失效方式

**Windows 路径直接语法错误**：`C:\Users\...` 在非 raw 字符串里会触发 `truncated \UXXXXXXXX escape`。这一次至少报了错。

**替换静默不生效**：要替换的串和文件实际内容差一个反斜杠，`replace` 什么也不做，也不报错。看起来「补丁打完了」，实际上文件一个字节没变——比报错更贵，因为它让你基于错误的前提继续往下走。

根子在于 heredoc 有两层转义：bash 一层，Python 字符串字面量一层。改文件就用编辑工具，heredoc 只留给不含转义层的纯执行命令。

## 两个验证手法

```python
# 二进制层面确认没有控制字符混入
assert open(p, 'rb').read().count(b'\x08') == 0

# 语法层面：compile 比 ast.parse 严
compile(open(p, encoding='utf-8').read(), p, 'exec')
```

`compile()` 能拦下 `ast.parse()` 放过去的问题，比如 `nonlocal` 绑定错误、非 async 函数里用 `await`。
