# 别把全量数据读进内存

**在生产服务器上跑分析脚本，必须逐单元流式处理，并且给进程设一个内存上限。**

## 为什么

一次回测把 140 万行因子 + 80 万根 K 线一次性读进 Python dict，估算 1GB+。

那台机器同时跑着实盘和 9 个容器，**可用内存常年只有 200~300MB**，swap 已经用掉 1.3GB（健康巡检早就告警过「可用仅 247MB」）。

结果不是「脚本慢」，是**整机被压到 SSH 都连不上**——登录进程自己也要内存。面板报 530 源站失联，最后只能靠等内核 OOM 或硬重启恢复。

**不是容器挂了，是一台机器被一个分析脚本拖死。**

## 怎么用

- 在服务器上写脚本，先问一句「这东西最坏情况占多少内存」；超过 100MB 就要改设计
- 默认模板：**逐单元读 → 处理 → 释放**，绝不 `SELECT *` 全表进 list / dict
- 加一道自限，宁可脚本自己 `MemoryError` 死，也不要拖垮同机的生产服务：

```python
import resource
resource.setrlimit(resource.RLIMIT_AS, (900 * 1024 * 1024, resource.RLIM_INFINITY))
```

- 重活可以在**本地**跑：只从服务器捞需要的那几个单元（scp 小样本），本地算完再回传结果

## 判断哪个资源更紧

这台机器的**内存比磁盘紧得多**——磁盘还剩 17GB，内存常年只剩两三百 MB。

「机器还有空间」这句话必须指明是哪一种资源。
