# CI 红了先看分支落后多少

**PR 的 CI 确定性失败时，先量一下分支落后主干多少个提交，再谈 flake。**

## 为什么

一次真实的排查：PR 的 CI 稳定在同一个用例上失败，三次重试都挂在同一行。第一反应是「环境问题，重跑」。

实际上 CI 用的是 `pull_request_target`：**workflow 文件来自基分支，checkout 的却是 PR head 的代码**。于是主干上早就修好的测试，在这个 PR 里仍按旧版跑，必然失败。

那次分支落后 22 个提交。主干上有人把写死的账号昵称改成了正则，而这个 PR 里还是旧的那行。合并主干后一次通过。

## 怎么用

**先量差距**：

```bash
git rev-list --left-right --count origin/main...origin/<branch>
```

**再对拉同一个文件**：

```bash
git show <PR head>:<spec 路径>
git show origin/main:<spec 路径>
```

两边不一样，基本就是落后所致，合并主干即可——不用重跑，也不用改测试。

**区分确定性失败和 flake**：同一行三次尝试全败，是确定性的。真正的 flake 是随机的、换一次就过。

## 一条推论

**「测试挂了」有四种可能**：代码不对、测试不对、环境不对、**版本不对**。最后一种最容易被跳过，因为它看起来像前三种。
