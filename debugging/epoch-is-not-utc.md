# epoch 不一定是 UTC

**数据库里的 epoch 整数，默认当作 UTC 之前先核一遍——很多写入方存的是本地时间。**

## 为什么

某张表的 `ts` / `first_seen` 存的是服务器**本地时间**（CST+8）的 epoch，不是 UTC。SQL 里写：

```sql
date(ts, 'unixepoch')   -- 按 UTC 渲染，整体偏 8 小时
```

查「今天的调用量降了没」，结果显示今天只有 187 条、前几天都是 750+，一眼像是上游挂了；另一个数据源今天 23 条 vs 昨天 258 条，更像抓取中断。

**实际两组数字都只是「半天」**——UTC 的「今天」只覆盖到本地 14:28 为止。前面几天的「整天」也是 08:00→08:00 的错位窗口。

换成按本地 0 点分桶后：今天 659 vs 昨天同刻 867，另一个源 127 vs 137——完全正常。绕了七八次查询才发现是自己分组错了。

## 怎么用

分桶和展示一律用：

```sql
datetime(col, 'unixepoch', 'localtime')
```

或者在应用层按本地 0 点算 epoch 边界。

**判断「今天是否异常」必须同日同刻对比**，别拿半天比整天。

## 推广

换成一张新表、一个新库，做法是先核一次口径：

```sql
SELECT MAX(col) FROM t;   -- 和 `date +%s` 比，看差多少
```

差 0 是 UTC，差 28800 是 UTC+8，差出别的数就说明写入方有别的假设。
