# mock 全绿，不等于修好了

**用户说「问题在这条路径上」时，就得在那条路径上实测。**

## 为什么

一次修复：用户对某个页面提出意见。我看到 PR 里确有一版用例改成先切到正确的选项卡、且本地通过，就回复「已由某个提交落实，只是评审状态没更新」。

用户回：「修复我要求的。」

去真实应用里跑，发现**根本没修好**：进入页面后立刻读取，拿到的是全量列表（包含一堆没配置的条目），大约 3 秒后才收敛。原因是两个请求的返回顺序不确定，其中一个先到时，用于过滤的列表还是空的，过滤函数原样放行了全部。

而用例里的 mock 让那个请求**立即返回**，竞态被完全掩盖。**mock 通过 ≠ 真实路径修好。**

## 怎么用

- 涉及网络时序、异步初始化、真实凭据的修复，写完 mock 用例后**再在真实应用里跑一遍**
- 采样要在「刚进入页面的第一时间」连续多次读取——竞态只在第一瞬间暴露，单次读取可能恰好落在稳定态
- **用户否决你的判断时，先假设用户是对的**，去取证，别急着解释
- 反向对照最有力：旧代码能复现、新代码不能，因果关系就成立了

## 一条推论

**测试证明的是「在测试的条件下成立」。** mock 越干净，离真实条件越远。它不是错，但它不是证据。
