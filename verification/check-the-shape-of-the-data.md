# 交付前先看数据的「形」

**「取最新一条」是最容易悄悄串维度的写法。**

## 三个真实案例

**① 少了分组条件。** 一张表是「对象 × 来源 × 截面」一行。取全序列首尾时没按来源分组，拿 A 来源最早的一行比 B 来源最新的一行——算出了「+959.62%」这种离谱数字，一整条结论作废，而对方已经在面板上看到了。

离谱值反而安全，它自己会暴露。**真正危险的是差 2–3 倍那种**，看着完全合理。

**② 单位已经被换算过。** 某个数量列**入库时**就已经除过精度、存成了人类可读的值。重建时又除了一遍，于是全部缩小到原来的 1/10^n。

症状是每一层都「看起来正常」：数据照常产出、界面照常显示。唯一异常是「单笔超过 10 万」这条**按金额分档**的规则永远不触发，而小额被凑成了「连续 3 笔」。

面板上其实显示过 `$0.50`、`$0`——看见了，但当成显示格式问题去改了格式化函数，没往上游追。

**看到明显不合理的量级，先修数据，不要修显示。**

**③ 样本里混进了不该有的东西。** 结果里出现一个「看着眼生」的标的名，心里过了一下「可能是某类衍生品？」就放过了。第二天看到一堆才去查——结果是一批本该被过滤掉的类别污染了回测样本池。剔掉之后结论强度整个变了：从「明显能赚」变成「勉勉强强」。

## 怎么用

**看到 `ORDER BY ... LIMIT 1`，先问「这张表还有没有别的维度没限定」。**

**用数值列之前，先确认它入库时有没有被换算过。**

**看到陌生的样本名，必须追一句它是什么**，不能当成「可能只是我没见过」。

三条的共性：**这些错误都不会抛异常，只会让数字「看起来还行」。**

交付前跑一遍：

```sql
SELECT <维度>, COUNT(*) FROM <表> GROUP BY <维度>;
SELECT <数值列> FROM <表> LIMIT 5;   -- 看一眼量级对不对
```

拿一个你知道真实值样本对一次，比看一千行汇总有用。
