# 浏览器改动自己跑一遍再交付

**涉及浏览器行为的改动——脚本、CSS、DOM 操作、页面布局——自己起服务器实测，不要交代码让用户去试。**

## 为什么

有一次修一个用户脚本，我交付了代码，外加一段「你贴到控制台跑一下，把输出发我」的诊断片段。用户回了一句：**「你自己打开浏览器测。」**

实测当场抓到两个纯静态审阅发现不了的问题：

1. **CSS 嵌套让所有样式规则都带一个空的 `cssRules`**。我的逻辑用「有没有 `cssRules`」来判断是否条件组，结果永远走不到检查 `max-width` 那一步——嵌套规则也是个 `cssRules`，只是空的。
2. **`max-width: var(--x, 760px)` 这类写法静态解析不出来**。变量还在，字面值不在。

这两个问题读代码都读不出来，跑一遍就现形。

## 怎么用

**流程**：起本地服务器 → 打开页面 → 用脚本断言**具体数值**（宽度、计算样式，不是「看起来对」）→ 截图看视觉。

**拿不到真实站点时**（需要登录、外链被拦），先用 curl 抓真实页面的 HTML / CSS 当依据，照真实结构做本地复刻，**不要凭记忆猜**。

**注意**：

- 临时设的视口尺寸，收尾时还原
- 本地 mock 的 `<script src>` **要带防缓存参数**：`document.write('<script src="....?v=' + Date.now() + '">')`。`python -m http.server` 不发 `Cache-Control`，浏览器会启发式缓存——我就这样读到过旧版脚本，看到「改了没生效」的假象，差点误判成 CSS 写错
- 断言之前，先确认注入的样式里**确实含本次新增的那一行**

## 一条推论

**「静态看是对的」和「跑起来是对的」之间，隔着一次实测。** 越接近渲染层的改动，这个差距越大。
