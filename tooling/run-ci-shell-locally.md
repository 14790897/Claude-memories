# CI 的 shell 逻辑，本地就能跑

**改 workflow 里的脚本时，把 `run:` 块抽出来在本机跑，不要推上去等 CI。**

## 为什么

一次改通知脚本的截断逻辑，靠本地复跑拿到 8/8 用例的证据才提 PR，比「推一版、等队列、看日志、再推」快一个数量级。

但复跑本身有两个坑，各浪费了一轮：

**抄脚本会失真。** 手抄一份进测试文件，测的是「我以为的脚本」，不是真实文件。要从 yml 里抽：

```bash
awk '/^        run: \|$/{f=1;next} f' .github/workflows/x.yml | sed 's/^          //'
```

然后替换掉 `${{ }}` 模板行、去掉最后真正发请求的那条 curl，用假的事件 JSON（`jq -n` 造）喂进去。

**Windows 版 jq 会在 stdout 上做 LF→CRLF 转换**（Linux runner 不会）。字符串比对时凭空多出 `\r`，看起来像逻辑错了。比对前 `tr -d '\r'` 归一化，或者先确认内容本身没被改。

## 怎么用

- 断言失败时，**先怀疑工具链（换行、逐行读、编码），再怀疑逻辑**
- `-R` 不加 `-s` 是逐行读，会吞掉换行；要整段读就加 `-s`
- **别拿命令替换出来的变量做长度或相等判断**：`$(...)` 会吃掉末尾换行，「超出部分是换行」的输入会被误判成没截断。要判断长度就直接读原始事件 JSON
- 非 BMP 字符（emoji）按码点截断不会被切坏，可以放心用 `.[0:n]`

## 一条推论

**能在本地验证的东西，就不要用 CI 当调试器。** CI 是最终确认，不是 REPL。
